# Daemon Fix Plan — igautomation

## Overview

The daemon has 9 completed sessions in the database, but all were `discovery` strategy. The profiling, monitoring, engagement, and content_engagement strategies have never executed — partly due to LLM planning failures, partly due to code bugs. 96% of 530 accounts lack profile data. Growth tracking, content engagement, and collection management are all non-functional due to implementation gaps.

This plan addresses 21 items: 10 bugs (P0–P2), 5 architectural issues (P3), and 6 improvement/refactor opportunities discovered during investigation.

## P0 — Critical Bugs (Crashes / Makes Strategies Unusable)

### Fix 1: Content Engagement SQL — `status` → `engagement_status`
**File**: `src/igautomation/daemon/loop.py` lines 472–478
**Problem**: Query references `WHERE status = 'pending'` but the column is `engagement_status`. This `no such column` error crashes `_execute_content_engagement` silently every time.
**Action**: Change `status` to `engagement_status` on line 474. Also update line 474 from `'loaded'` to `'analyzed'` since content items are set to `analyzed` after LLM processing, not `loaded`.

### Fix 2: LLM API Key Not Loaded in DaemonLoop
**Files**: `src/igautomation/daemon/loop.py`, `src/igautomation/daemon/__main__.py`, `src/igautomation/cli.py`
**Problem**: `DaemonLoop.__init__()` never loads `.env` file or checks `os.environ` for API keys. Only `__main__.py` does, but CLI `igx daemon start` doesn't. LLM planning silently fails every session.
**Action**:
1. Add a `_load_env_config()` static/class method to `DaemonConfig` (in `strategies.py`) that scans `os.environ` and a `.env` file for `OPENPAI_API_KEY`, `OPENPAI_BASE_URL`, `LLM_MODEL`.
2. Call it in `DaemonLoop.__init__()` before storing config — so ALL startup paths (CLI, `python -m`, direct instantiation) benefit.
3. Remove the duplicate env-loading code from `__main__.py` (lines 48–74) since it's now centralized.
4. Add identical env loading to the `start()` and `session()` CLI commands in `cli.py` for the direct `DaemonConfig(db_path=...)` path.
5. Add a `--no-llm` flag to disable LLM planning explicitly.

### Fix 3: `content_engagement` Missing from AccountCollector Dispatch
**File**: `src/igautomation/scraper/collector.py` lines 703–712 and 725–746
**Problem**: `content_engagement` is listed in `DaemonConfig.default_strategies` and `FALLBACK_PLANS` but does NOT exist as a strategy name in `AccountCollector.collect()`. If a session tries to run "content_engagement" as a discovery sub-strategy, it hits `case _` with a warning log.
**Action**: Add `"content_engagement"` to the `all_strategies` list, but make its `case` arm a no-op with a clear log message, since content engagement is handled by `_execute_content_engagement()` in the daemon loop, not the collector. Alternatively, remove it from `default_strategies` and keep it as a daemon-level strategy only.

## P1 — High Priority (Produces Wrong/Silently Incomplete Results)

### Fix 4: Only Discovery Runs — No Profiling/Monitoring/Engagement Diversity
**File**: `src/igautomation/daemon/loop.py` — `_run_forever_async()` and `_get_llm_plan()`
**Problem**: With LLM planning broken (Fix 2) + `_plan_index` cycling through fallback_plans, the daemon still only ran discovery 9/9 times. Two error sessions and short run duration explain most of it, but the fallback cycling mechanism is fragile — if LLM planning fails, the index increments but only 4/8 fallback plans are non-discovery, and `content_engagement` plans error out due to Fix 1.
**Action**:
1. After Fix 1 and Fix 2, the diversity problem largely resolves itself (LLM planning will work and suggest appropriate strategies).
2. Add a **strategy diversity guard**: if the last 3 sessions used the same strategy, force the next session to use a different one (profiling or monitoring).
3. Add a **scheduled profiling trigger**: every 6 hours, regardless of LLM choice, run a profiling session if >100 accounts are unenriched.

### Fix 5: Growth Status Never Computed After Monitoring
**File**: `src/igautomation/daemon/loop.py` — `_execute_monitoring()`
**Problem**: `_execute_monitoring()` records snapshots via `db.add_follower_snapshot()` but never calls `db.refresh_growth_for_all()` or `compute_growth_status()` after completion. Growth data accumulates but is never processed.
**Action**: After the monitoring loop completes (after line 408), add an `await db.refresh_growth_for_all()` call. This will compute `growth_status` and `growth_rate` for all accounts with ≥2 snapshots after each monitoring session. Also add the same call to `_execute_profiling()` since profiling also gets initial follower counts.

### Fix 6: Content-Collections Links Never Created
**File**: `src/igautomation/daemon/loop.py` — `_execute_content_engagement()`
**Problem**: Content items get analyzed and saved to DB, but the `content_collections` join table is never populated. `ContentEngager._add_to_collection_via_js()` clicks UI elements but the daemon path never calls `db.upsert_collection()` + `db.add_content_to_collection()`.
**Action**: After the LLM analysis succeeds (around line 528), extract the `llm_collection_suggestion`, call `db.upsert_collection(name=suggestion)`, then `db.add_content_to_collection(item_id, collection_id)`. Do this for the `content_engage()` CLI path too (it has the same gap at `cli_content.py` lines 249-335).

### Fix 7: Content Engagement Results Never Logged to content_engagement_log
**File**: `src/igautomation/daemon/loop.py` — `_execute_content_engagement()`
**Problem**: `ContentEngager.engage_content()` returns `ContentEngagementResult` but the daemon never calls `engager.log_engagement()` (which is async). The `content_engagement_log` table is empty despite 310 analyzed items.
**Action**: After `engager.engage_content(item)` succeeds (around line 500), call `await engager.log_engagement(item, result, session_id=self._current_session_id)` to record each action (like, save, watch, interested) to the engagement log.

### Fix 8: `accounts_discovered` Count Inflated
**File**: `src/igautomation/daemon/loop.py` — `_execute_discovery()`
**Problem**: `before = len(collector.accounts)` is always 0 (fresh collector per session), so `new_count = len(accounts) - 0` counts all collected accounts as "discovered" even if they already exist in DB.
**Action**: Instead of tracking collector set size, track the actual number of NEW accounts successfully upserted (i.e., where upsert resulted in INSERT vs UPDATE). Modify the save loop to count only when a NEW account is inserted. Query DB for pre-existing count before the discovery save loop begins, or track insert vs update from `db.upsert_account()` return value / a separate check.

### Fix 9: Discovery Event Strategy = Always "discovery" (Not Sub-Strategy)
**File**: `src/igautomation/daemon/loop.py` — `_execute_discovery()` line 304
**Problem**: All accounts discovered during a discovery session get `strategy="discovery"` in `discovery_events`, regardless of which sub-strategy actually found them.
**Action**: Track which sub-strategy found each account. The `AccountCollector.collect()` method should return a `dict[str, list[str]]` (strategy → usernames) OR the collector internally tracks provenance. Option A: Modify `AccountCollector._accounts` from `set[str]` to `dict[str, str]` (username → strategy). Option B (simpler, less invasive): In the daemon, save accounts with `strategy="discovery"` but append sub-strategies used to the `query_text` field as structured JSON so they can be queried later. I'll go with **Option B** since it doesn't change the collector's public API and avoids breaking existing tests.

**NEW APPROACH**: Actually, the cleanest approach is to store the collection strategy name during the save loop. Pass the strategy name from the discovery session's `plan.params.get("strategies", [])` into the discovery event's `source_username` or `query_text`. Store as `{"sub_strategies": ["graphql_suggestions", "cascade"], "seeds": ["z.subha_"]}` in `query_text`.

### Fix 10: Engagement Strategy Cannot Like Posts (dead max_likes)
**File**: `src/igautomation/daemon/loop.py` — `_execute_engagement()` lines 416, 437
**Problem**: The function reads `max_likes` from params and checks `likes_done >= max_likes`, but no code path ever calls a like action. Only `follow_user()` and `view_profile()` are used. `like_post()` requires a post URL, which the strategy doesn't have.
**Action**: Remove `max_likes` from the engagement fallback plan params and from the function's `max_likes` variable. Replace the likes_done check with a more useful action — like visiting the user's page and scrolling their recent posts (organic browsing). Alternatively, retrieve recent post URLs from GraphQL profile data and use those. For now, removing the dead code is the minimal fix. Add a `max_profile_views` param instead, which maps to the actions the function actually performs.

### Fix 11: Engagement Strategy Gated by Tier (Only 8 Accounts Eligible)
**File**: `src/igautomation/daemon/loop.py` — `_execute_engagement()` lines 420–424
**Problem**: The SQL requires `a.tier IS NOT NULL`, but 510/530 accounts have NULL tier. Only 20 accounts have tiers, and 12 have interactions — leaving only 8 eligible accounts.
**Action**: Change the query to also include accounts without tier data. Use `ORDER BY COALESCE(a.follower_count, 0) DESC, a.last_checked_at ASC NULLS FIRST` instead of `ORDER BY a.follower_count DESC` so it works even without tier. Update the WHERE clause to remove the tier requirement, or add an `OR a.tier IS NULL` so all accounts are candidates. Prioritize accounts that have never been checked.

## P2 — Medium Priority (Incorrect/Misleading Behavior)

### Fix 12: ProfileInfo.category Never Populated
**File**: `src/igautomation/scraper/analyzer.py` — `_analyze_one()` (~line 292)
**Problem**: `ProfileInfo` has a `category` field initialized to `""`, and `_analyze_one()` never sets it. The `_execute_profiling()` daemon method saves `category=profile.category` to DB, which is always empty.
**Action**: In `_analyze_one()`, after keyword matching, set `category` based on matched flags: `profile.category = "bd_model" if profile.is_bd and profile.is_model else "bd" if profile.is_bd else "model" if profile.is_model else ""`. This gives real values to the category field for filtering and reporting.

### Fix 13: Niche Case Sensitivity in Content Data
**File**: `src/igautomation/content/analyzer.py`
**Problem**: LLM returns niches with inconsistent casing: "Lifestyle" vs "lifestyle", "Art" vs "art". This creates duplicate keys in niche statistics.
**Action**: In `_analyze_with_llm()` and `analyze_content_browse()`, apply `.lower()` on `content_niche` before saving. Also apply `.strip().lower()` on `llm_collection_suggestion`.

### Fix 14: CLI Session Command Doesn't Load LLM Config
**File**: `src/igautomation/cli.py` — `session()`
**Problem**: Same LLM API key loading gap as Fix 2, but for the single-session `igx session` command. If the user passes `--strategy content_engagement`, the SQL bug (Fix 1) crashes it.
**Action**: After Fix 2 centralizes env loading, this is automatically resolved. Verify.

### Fix 15: `--db` Flag Override Bug in __main__.py
**File**: `src/igautomation/daemon/__main__.py` line 43
**Problem**: `if args.db and args.db != "igautomation.db"` — if the user explicitly types `--db igautomation.db`, the condition is False and the override is skipped.
**Action**: Change to `if args.db:` to always apply the CLI override when the flag is explicitly set. Remove the `!= "igautomation.db"` guard.

## P3 — Architectural Issues

### Fix 16: SessionScheduler Never Integrated
**File**: `src/igautomation/daemon/loop.py` — `_run_forever_async()`
**Problem**: The 273-line `SessionScheduler` with weighted activity patterns, cluster logic, and day boundaries was implemented but is never instantiated or called. The daemon uses simple `BehaviorConfig.cooldown_seconds()` with fixed ranges.
**Action**: Add `self._scheduler = SessionScheduler()` to `DaemonLoop.__init__()`. In `_run_forever_async()`, replace the fixed cooldown logic with `await asyncio.sleep(self._scheduler.seconds_until_next())`. Keep the sleep-hours check and daily limit check as overrides. Add a `--schedule-mode` config option (simple/weighted) defaulting to weighted.

### Fix 17: RateLimiter Never Used by Daemon
**File**: `src/igautomation/daemon/loop.py` — `_run_one_session()`
**Problem**: The 281-line async `RateLimiter` with exponential backoff is never instantiated. The daemon relies on `BehaviorEngine._delay()` (simple random sleep) for rate control.
**Action**: Instantiate `RateLimiter` in `DaemonLoop.__init__()` and pass it through to session execution methods. Wrap GraphQL calls and CDP navigation calls with `await self._rate_limiter.acquire()`. On errors, call `self._rate_limiter.record_error()` to trigger backoff. On success, call `self._rate_limiter.record_success()`. This gives the daemon intelligent self-regulation.

### Fix 18: Sync Code Blocks Async Event Loop
**Files**: `graphql/client.py`, `scraper/analyzer.py`, `scraper/collector.py`, `content/engager.py`
**Problem**: The daemon is async but all core operations are synchronous (`time.sleep`, sync WS, sync HTTP). Long-running blocking calls prevent concurrency and make the async architecture misleading.
**Action**: This is a large refactor. For this plan, take a minimal approach:
1. Wrap blocking calls in `asyncio.get_event_loop().run_in_executor(None, blocking_func, *args)` for GraphQL calls (the most latency-sensitive since they go to IG's API).
2. Keep CDP calls sync (they're local and fast).
3. This prevents the daemon from freezing during network calls while keeping change scope manageable.

### Fix 19: Daemon Analysis Never Runs Automatically
**File**: `src/igautomation/daemon/loop.py` — `_run_forever_async()`
**Problem**: `AnalysisEngine` exists but is never called by the daemon loop. The `analysis_log` table is empty.
**Action**: After every 5th session (or every 24 hours), run a quality review analysis and save results to `analysis_log`. Add a counter to track session count since last analysis. Call `AnalysisEngine.run_quality_review()` → `db.add_session_analysis()`. This gives the system self-awareness of data quality.

### Fix 20: ContentEngager Constructor Type Mismatch
**File**: `src/igautomation/daemon/loop.py` line 483
**Problem**: `ContentEngager(cdp, db)` is called from daemon with `db` being `AsyncDatabaseStore`, which matches the constructor's `store` parameter. The issue is that `engage_content()` is sync and never calls `self._store.log_content_engagement()` — the async method is in `log_engagement()` which is separate. This isn't a crash-bug but the engagement results have no record.
**Action**: After Fix 7 (logging engagement results), the type alignment with the AsyncDatabaseStore is fine. The real fix is to ensure `log_engagement()` is called after `engage_content()`. Consider making `engage_content()` return results that the async context (daemon loop) uses to call `log_engagement()` — which is already the pattern after Fix 7.

## Improvement & Refactor Opportunities (Discovered During Investigation)

### Improvement 1: Centralize LLM Configuration
**Files**: `daemon/strategies.py`, `analysis/analyzer.py`, `content/analyzer.py`, `cli.py`, `daemon/__main__.py`
**Problem**: LLM config is loaded in 4+ places with slightly different logic each time: `content/analyzer.py` has `_get_llm_config()`, `analysis/analyzer.py` checks `os.environ`, `daemon/__main__.py` loads `.env`, `cli.py` skips entirely.
**Action**: Create a single `igautomation/llm_config.py` module with a `LLMConfig` dataclass/pydantic model + a `load_llm_config()` function that scans env vars and `.env` file, caching the result. Replace all 4 loading sites with calls to this module.

### Improvement 2: Add Account Provenance Tracking to Collector
**File**: `src/igautomation/scraper/collector.py`
**Problem**: The collector's `_accounts: set[str]` tracks only usernames but not which strategy discovered each one, making analytics impossible.
**Action**: Change `_accounts` from `set[str]` to `dict[str, str]` (username → strategy_name). The `collect()` method updates the dict with strategy name on each addition. Modify the `accounts` property to return `set(self._accounts.keys())` to preserve backward compatibility. The `get_sorted()` method sorts by strategy then username for deterministic output. This enables Fix 9 (per-account discovery strategy tracking).

### Improvement 3: Add `content_engagement` Strategy to Daemon Loop (Not Collector)
**File**: `src/igautomation/daemon/loop.py`
**Problem**: `content_engagement` is in `default_strategies` but should be handled at the daemon level (it has its own `_execute_content_engagement()` method), not as a sub-strategy of discovery.
**Action**: Remove `"content_engagement"` from `DaemonConfig.default_strategies` (line 42 of `strategies.py`). It's already handled by the daemon dispatch at `_run_one_session()` case `"content_engagement"`. This is the correct separation — content_engagement is a daemon-level strategy, not a discovery sub-strategy.

### Improvement 4: Test Coverage for New Fixes
**Files**: `tests/test_daemon.py`, tests for new `llm_config.py`
**Problem**: Tests exist for basic daemon config and loop initialization but don't cover the fixed paths.
**Action**:
1. Add test for `DaemonConfig._load_env_config()` with mocked `os.environ`.
2. Add test for `_execute_content_engagement()` SQL fix (mock DB).
3. Add test for `refresh_growth_for_all()` being called after monitoring.
4. Add test for collection linkage creation.
5. Add test for `AccountCollector` with provenance dict.
6. Ensure existing 119 tests still pass.
